# 绑定流程与任务控制设计

日期：2026-09-24

## 背景

当前桌面端绑定流程有四个步骤。第三步只保存部分任务设置，推送设置仍需回到主面板；第四步要求用户手动处理代理断开。主面板的“立即执行”也只有一个入口，无法明确区分签到和分享。云端 `daily_runs` 目前按绑定和业务日期唯一，不能表达同一天的独立手动动作。

本次调整的目标是：登录态、任务设置和推送设置在第三步一次保存；保存成功后直接进入主面板；主面板提供独立的手动签到、手动分享入口；定时任务仍作为一个完整任务同时执行签到和分享；桌面端退出时强制关闭电脑代理并提醒用户关闭手机 Wi-Fi 代理。

## 需求边界

- 绑定向导保留三个步骤：连接与配置、抓包并验证、保存到云端。
- 第三步复制主面板的任务设置和推送设置。`不推送` 是有效配置，不能因为没有推送 key 阻止保存。
- 选择 Bark 或 Server 酱时，key 必须在保存前校验；绑定保存成功后再发送一次测试通知。测试通知失败不回滚绑定，界面显示可重试的警告。
- 主面板的“立即签到”和“立即分享”互相独立，均只操作已绑定账号；不依赖是否配置推送。
- 云端定时任务是唯一的组合任务，按一次任务记录同时执行签到和分享。手动操作不触发另一项。
- 绑定能力固定要求支持分享，移除 `can_share` 及页面上的分享能力开关；历史数据迁移后定时任务固定执行分享。
- 去掉第四步、断开连接页面和保存完成页。退出应用时停止电脑代理，并提示用户手动关闭手机上的 Wi-Fi 代理；提示确认后允许退出，避免浏览器关闭后无法再次打开客户端。

## 现状与约束

- 桌面端通过 `desktop/local_api.py` 暴露绑定、运行和抓包控制，`desktop/binding.py` 负责调用云端 API。
- 云端运行入口是 `POST /v1/binding/runs`，后台 runner 负责领取 `daily_runs` 并执行签到、分享和通知。
- `daily_runs` 当前有 `UNIQUE(binding_id, business_date)`，且 `do_share` 记录了是否分享。
- 绑定保存与通知配置目前是两个请求，激活接口拒绝 `notifications` 字段，需要改为同一次激活请求处理。
- 电脑代理的生命周期由桌面端 `ProxyManager` 管理；退出 Tk 窗口时必须先执行停止，再销毁窗口和本地服务。

## 数据模型

### 运行记录

在 `daily_runs` 增加 `run_type`：

- `scheduled`：云端定时任务，执行签到和分享。
- `manual_sign`：主面板手动签到，只执行签到。
- `manual_share`：主面板手动分享，只执行分享。

为保留重试和审计能力，手动动作每次点击创建一条新记录；定时任务每天最多创建一条。迁移时重建 `daily_runs` 表，去掉原有的表级唯一约束，增加 `run_type NOT NULL DEFAULT 'scheduled'`，并建立部分唯一索引 `UNIQUE(binding_id, business_date) WHERE run_type = 'scheduled'`。已有记录全部标记为 `scheduled`，其状态和结果原样保留。

运行记录列表和管理端展示 `run_type`、触发来源、签到状态、分享状态、通知状态及错误信息。手动签到记录的 `share_status` 固定为 `skipped`，手动分享记录的 `sign_status` 固定为 `skipped`，以便沿用现有状态和统计组件。

`do_share` 在迁移期间保留以兼容旧记录和旧客户端读取，但新写入的定时任务固定为分享；后续清理阶段再删除该字段。`can_share` 在绑定表中迁移为固定能力后删除，绑定激活时必须有可用的分享上下文，否则返回明确错误。

### 通知配置

激活请求可携带 `notifications`。云端在创建 binding 的同一个事务中校验并加密配置，写入 `notification_config` 和 `notification_summary`。`不推送` 写入空配置和关闭状态；Bark、Server 酱仍使用现有加密格式。通知测试发生在绑定事务提交后，失败只影响提示和 `notification_status`，不撤销 binding。

## API 设计

### 激活并保存配置

`POST /v1/binding-candidates/{id}/activate`

请求继续包含账号标签、执行时间和兼容字段，同时增加：

```json
{
  "label": "账号用户",
  "scheduleTime": "00:00",
  "notifications": {
    "channel": "none"
  }
}
```

`channel` 允许 `none`、`bark`、`serverchan`。选定渠道时携带对应 key；服务端拒绝空 key、未知渠道和未能解密/加密的配置。激活响应返回完整 binding 视图和通知摘要，桌面端据此切换主面板。

### 手动运行

`POST /v1/binding/runs` 请求体：

```json
{ "runType": "manual_sign" }
```

`runType` 只允许 `manual_sign`、`manual_share`；缺省值仅供旧客户端兼容，按 `scheduled` 处理。接口返回新建运行记录的 id 和状态。调度器调用后台 runner 时仍使用 `scheduled`，不复用手动动作的记录。

桌面端本地 API 保留 `/api/binding/run` 作为兼容入口，同时增加 `runType` 参数。主面板两个按钮分别传入 `manual_sign` 和 `manual_share`；定时任务路径不变。

## 桌面端交互

### 第三步

- 显示账号预览、执行时间下拉框和推送渠道分段控件。
- `不推送` 选中时隐藏 key 输入和测试提示，保存按钮可直接提交。
- Bark/Server 酱选中时显示 key 输入；为空时阻止提交并聚焦输入框。
- 保存按钮只发一次激活请求；成功后跳转主面板，不再展示第四步。
- 激活成功后异步测试已配置的通知渠道，测试失败在主面板顶部显示警告，不阻止任务运行。

### 主面板

- 任务设置保留执行时间和暂停/恢复。
- 将原来的单个“立即签到”按钮拆成“立即签到”和“立即分享”两个按钮。
- 两个手动按钮在 binding 存在且状态允许运行时可用；`不推送` 不影响可用性。
- 运行记录区域显示当前动作、时间、状态、签到/分享结果和通知结果；正在执行时禁用对应按钮，完成或失败后恢复。

### 退出

退出、窗口关闭和异常关闭路径统一调用停止电脑代理。停止完成后显示一次提示：“电脑代理已关闭，请在手机 Wi-Fi 设置中关闭代理，否则可能导致网络异常。”提示确认后继续退出。若代理已经停止则不重复执行停止操作，但仍在检测到手机代理状态为活动或最近使用时显示提醒。

## 云端执行逻辑

runner 根据 `run_type` 选择动作：

- `scheduled`：按现有租约、凭证版本和重试机制执行签到，然后读取分享素材并执行分享；两步都完成后标记 `completed`，部分成功标记 `partial`。
- `manual_sign`：只执行签到，跳过分享；结果写入同一条运行记录。
- `manual_share`：只执行分享；如果分享所需上下文缺失，记录明确错误码，不尝试签到补救。

通知发送继续由运行记录的最终状态驱动。没有通知渠道时把 `notification_status` 标记为 `skipped`，不能把任务整体标记为失败。

## 错误处理与兼容

- 激活保存失败时保留候选和桌面端表单，允许修正后重试。
- 通知测试失败不回滚 binding，主面板允许重新保存并测试。
- 手动运行返回冲突或已有运行时，桌面端显示正在执行的记录，而不是卡住按钮。
- 旧客户端不传 `runType` 时仍按定时任务兼容；新客户端始终显式传值。
- 数据库迁移失败时不启动新 runner，并保留旧表备份名，便于回滚。

## 测试计划

- Cloud 单元测试：运行记录迁移、三种 `run_type` 的动作选择、定时任务唯一性、手动动作可重复、通知为空和通知测试失败不回滚。
- Cloud 接口测试：激活时原子保存通知配置、手动签到/分享请求校验、旧客户端兼容。
- Desktop 测试：第三步表单提交一次、无推送也能保存、渠道 key 校验、两个按钮传递不同 `runType`、退出时强制停止代理并显示手机代理提示。
- 回归测试：现有登录、抓包、绑定、定时任务、推送测试和打包 smoke test。

## 发布与迁移顺序

1. 先发布数据库迁移和兼容 runner，支持旧记录和新 `run_type`。
2. 发布 Cloud API，接受带通知配置的激活和手动运行类型。
3. 发布桌面端三步流程、主面板按钮和退出处理。
4. 观察运行记录与通知状态后，再删除 `can_share`、旧 `do_share` 兼容逻辑和第四步残留代码。
