# 本地一键提取指南（Windows + WSL2）

> 目标：在本地 Windows 机器上全自动提取领克 App 的 `nativeAppKey` /
> `nativeAppSecret`，写入 `env.json`，不依赖 macOS、不依赖 CI。
>
> 一键命令（WSL 内）：
>
> ```bash
> python3 LynkCoHelper/tools/extract_appsecret_x86_local.py
> ```

## 1. 结论先行

| 事项 | 结论 |
| --- | --- |
| 可行路线 | **x86_64 系统镜像 + KVM 加速**，加固壳（仅 arm64 .so）经 libndk 翻译执行 |
| 不可行路线 | arm64 镜像本地跑：qemu fork 对无 PCI 总线的 ranchu 无条件初始化 virtio-snd，`PCI bus not available` 必死，无参数可绕 |
| 冷启动耗时 | x86_64 + KVM 约 2~5 分钟（arm64 TCG 要 20~50 分钟且必死） |
| 提取产物 | `env.json` 的 `secrets.nativeAppKey` / `secrets.nativeAppSecret` |
| 复跑成本 | 模拟器在线时 30 秒内出结果 |

## 2. 为什么 arm64 路线本地必死（根因分析）

### 2.1 现象

31.3.10 与 36.2.12 两个版本的 emulator，arm64 镜像启动后数分钟内 qemu
退出，日志含：

```
emulator: ERROR: PCI bus not available for virtio-snd-pci
```

### 2.2 排查过程

1. **参数面排查（全部无效）**：`-no-audio`、`-audio none`、
   `-feature -VirtioSnd`、`-nodefaults`、`-qemu -nodefaults`、
   `-qemu -audiodev`、`setarch -R`。qemu 的 fork（`qemu-system-*`）在
   machine init 里**无条件**调用 virtio-snd 创建，音频配置 gate 不生效。
2. **二进制手术尝试（证据链完整但放弃）**：
   - `grep -abo 'PCI bus not available'` 定位格式串文件偏移 `0x2EF400`；
   - `readelf -l` 得到段映射（`.text` 在段 2，vaddr = fileoff + 0x1000）；
   - 用 rip 相对引用扫描 + RELA 重定位扫描找引用点 → 该串**既无代码
     引用也无静态重定位**，说明指针由运行期构造函数写入 `.data`，静态
     定位创建调用点不可行；
   - 动态路线：gdb 断 `error_report` 因二进制 stripped（仅存
     `.gnu_debuglink`，无 `.symtab`）不可用；断 libc `vfprintf` 记录
     每次输出的调用栈，PCI 报错前的那条即创建链 —— 可行但每次 gdb
     会话 3~6 分钟，且还要继续定位 caller 的 caller 才能 NOP。
3. **决策**：x86_64 镜像 + KVM 路线成本远低于 qemu 二进制手术，且
   脚本原生支持（`extract_appsecret_auto.py` 的实验模式），故弃手术。

### 2.3 arm64 路线如果非要救活（备用方案，未走完）

- 路线 A：gdb `break vfprintf` + 全量调用栈日志，找到 `virtio-snd`
  创建调用链中 machine init 的调用点 → python 计算文件偏移 →
  NOP 掉那条 `call`（3 字节左右）→ 打补丁的 qemu 副本跑 arm64。
- 路线 B：35.x 版本的 emulator fork 修过此问题（CI 上 arm64 能跑通
  即证据），从自有 GitHub Actions 构建日志里挖 35.x 的 build id，
  `sdkmanager "emulator;35.x.y"` 钉版本。

## 3. 三个本地环境专属大坑（macOS/CI 不复现）

### 3.1 IPv6 坑（最隐蔽，致命）

`jdb -attach 18710` 会把 `localhost` 解析成 `::1`（IPv6），而
`adb forward tcp:18710` 的监听**只绑 127.0.0.1（IPv4）**。WSL2 的
`/etc/hosts` 把 `localhost` 同时映射到 v4/v6 且 JVM 默认优先 v6
的结果是：jdb 永远 `Connection refused`，而 python 探测（显式
`127.0.0.1`）却能握手成功——极具迷惑性，曾浪费数小时。

**修法**：一律 `jdb -attach 127.0.0.1:端口`。`appsecret_core.py` 与
一键脚本均已修复。

### 3.2 forward 生命周期坑

JDWP 注册出现**之前**建立的 forward，被 adbd 绑在空端点上；此后对
同一 `tcp:PORT` 重复下发 forward 是 **no-op**（不会重建监听），连接
永远 refused，必须先 `forward --remove` 或直接换新端口。一键脚本
每轮重试用全新端口（18800 起循环复用），简单可靠。

### 3.3 探测握手坑

App 处于 `-D` 等待调试器状态时，任何"连上就断开"的探测（python
握手测试、expect 超时被 kill 的 jdb）都会让 VM **自杀**（pid 消失，
forward 随之失效）。表现为：探测握手 OK → 紧接着 attach refused。

**修法**：jdb 一旦 attach 成功就让它走完整个提取流程，绝不提前
kill；调试期间也不要用裸 socket 做握手测试。

### 3.4 附加坑：wsl.exe 会话结束杀后台进程

`wsl.exe` 会话退出会对整个进程组发 SIGTERM，`nohup` 只挡 SIGHUP
挡不住它。后台跑提取必须：

```bash
cd /root/lynkco-helper
setsid nohup python3 LynkCoHelper/tools/extract_appsecret_x86_local.py \
    > /root/extract.log 2>&1 < /dev/null &
```

## 4. 一键脚本做了什么

`tools/extract_appsecret_x86_local.py` 的流程：

1. **设备检测**：`adb devices` 已有 `emulator-*` 在线 → 直接复用；
   否则 `core.find_emulator()` + `core.cold_start_and_wait(emu, avd)`
   无头冷启动（约 2~5 分钟，`/root/.lynkco-helper-tools/emulator.log`
   有完整启动日志）。
2. **App 检测**：`pm list packages` 未发现领克包 → 优先装
   `TOOLS_DIR/lynkco-v*.apk`（本地已有 4.2.7），本地没有才走官方
   接口下载最新版（约 285MB）。
3. **提取主循环**（最多 3 轮）：
   - `am force-stop` → `am start -D -n <壳入口 Activity>`（挂起等调试器）；
   - `pidof` 轮询拿 pid（60 秒）；
   - forward + `jdb -attach 127.0.0.1:<新端口>` 循环重试（窗口默认
     420 秒；被拒 = JDWP 尚未注册，libndk 下运行时初始化要几分钟，
     注册完成后一发命中，实测 0.4 秒附着）；
   - `suspend` → `stop in com.safe.cons.LynkCoConstants$g.<clinit>`
     （延迟断点）→ `resume`；
   - 等 `Breakpoint hit`（最长 300 秒）→ `next` ×15 逐步探 `c` 字段
     （壳在断点行之后才赋值）→ dump `b/c/d/e`；
   - `parse_field` + `looks_valid` 校验（key=9 位数字，secret=32 位
     小写字母数字）→ 写 `env.json`（`LYNKCO_AUTO_WRITE=1` 免确认）。
4. 任一轮成功即退出；三轮全败打印排障指引并退出非零。

## 5. 环境前置（一次性，已完成则跳过）

工具统一装在 `~/.lynkco-helper-tools/`（不污染项目目录）：

| 路径 | 内容 | 来源 |
| --- | --- | --- |
| `platform-tools/` | adb / fastboot | Google 官方 zip |
| `jdk8/` | Corretto 8（jdb 所在） | Amazon Corretto |
| `sdk/emulator/` | emulator（linux_x64 最新） | Google 官方 zip |
| `sdk/system-images/android-33/google_apis/x86_64/` | x86_64 系统镜像（API 33） | Google 官方 zip |
| `lynkco-v*.apk` | 领克 App 离线包 | 官方接口下载 |
| `~/.android/avd/lynkco_helper_avd_x64/` | AVD（手工生成 ini，免 avdmanager） | auto 脚本生成 |

首次从零搭环境：直接跑一次 `extract_appsecret_auto.py`，它会自动
下载上述全部组件并建 AVD；之后日常提取用本指南的一键脚本。

Python 依赖只有 `pexpect`（core 会自动 pip 安装，PEP 668 环境自动
附加 `--break-system-packages`）。

## 6. 常用命令速查

```bash
# 一键提取（前台）
python3 LynkCoHelper/tools/extract_appsecret_x86_local.py

# 一键提取（后台，wsl 会话关闭也不死）
cd /root/lynkco-helper
setsid nohup python3 LynkCoHelper/tools/extract_appsecret_x86_local.py \
    > /root/extract.log 2>&1 < /dev/null &
tail -f /root/extract.log

# 模拟器状态
~/.lynkco-helper-tools/platform-tools/adb devices

# 当前注册了 JDWP 的进程（采样安全，不会惊动挂起 App）
timeout 3 ~/.lynkco-helper-tools/platform-tools/adb jdwp

# 手动冷启动模拟器（无头）
setsid nohup ~/.lynkco-helper-tools/sdk/emulator/emulator \
    -avd lynkco_helper_avd_x64 -no-snapshot-load -no-window \
    -gpu swiftshader_indirect -no-audio -no-boot-anim \
    > ~/.lynkco-helper-tools/emulator.log 2>&1 &

# 看模拟器启动日志（排查 boot 卡住）
tail -40 ~/.lynkco-helper-tools/emulator.log
```

## 7. 排障速查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| jdb 永远 `Connection refused`，但 python 显式 `127.0.0.1` 能握手 | IPv6 坑（3.1） | 用 `jdb -attach 127.0.0.1:端口`（已修复） |
| forward 存在但连接 refused；换端口立即好 | forward 生命周期坑（3.2） | 每轮换新端口（已修复） |
| 探测握手 OK 后 App PID 消失 | 探测握手坑（3.3） | 别探测；jdb attach 成功后走完全程 |
| `PCI bus not available for virtio-snd-pci` | 用了 arm64 镜像 | 换 x86_64 镜像（本文档路线） |
| App 秒退、`pidof` 拿不到 | 壳在 libndk 下崩 / ABI 不对 | `adb shell logcat -d -b crash -t 60` 看崩溃缓冲 |
| 三轮都"未命中断点，直接 dump" 且字段为 null | 断点没抢在 `<clinit>` 前 | 确认 `am start` 的 `-D` 没丢；重跑一轮 |
| 提取值格式异常 | jdb 输出与命令错位 | 自动重试机制处理；连续出现则换轮次 |
| 后台进程莫名消失 | wsl.exe 会话 SIGTERM（3.4） | `setsid nohup ... &` 启动 |

## 8. 成功判据

日志出现：

```
[RESULT]
    nativeAppKey    = 9 位数字
    nativeAppSecret = 32 位小写字母数字
[+] 已写入 .../env.json
```

`env.json`（已被 gitignore 保护，不入库）的 `secrets` 段即包含
`nativeAppKey` / `nativeAppSecret`，签到脚本（`lynkco_daily_tasks.py`
等）可直接使用。
